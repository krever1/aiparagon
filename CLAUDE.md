## Shared gotchas
- n8n update_workflow doesn't activate; always publish_workflow after.
- n8n workflow description max 255 characters, fails silently past it.
- n8n update_workflow copies each node's credential from the saved workflow when the node keeps its name and type, HTTP Request nodes included, and keeps node positions (n8n's own update code, read Oct 21). Its note that HTTP Request nodes "were skipped during credential auto-assignment" lists every HTTP node and only means none was picked for it automatically. A renamed or new node gets nothing copied: an HTTP Request one needs its credential set in the editor. get_workflow_details never shows credentials.
- To rebuild a workflow without retyping it: export it with get_workflow_details, turn it into SDK code with `generateWorkflowCode` from @n8n/workflow-sdk, change it, and parse it back with `parseWorkflowCode` to diff before update_workflow. Non-trigger nodes lose their webhookId (n8n gives them new ones).
- n8n resource locator needs mode "list" + cachedResultName to publish.
- n8n update_workflow leaves the workflow's settings as they were: a timezone sent in the code on Oct 19 (Strategy Insights) didn't stick. Change settings in the editor.
- In Claude Code cloud sessions the outbound proxy can block n8n.aiparagonconsulting.com, supabase.co, aiparagon.vercel.app and fbcdn.net for curl and browsers (seen Oct 20). The n8n, Supabase and Vercel MCP tools still work, and the Vercel one fetches a deployment's pages.
- Vercel skips a deployment it takes for a duplicate. On Oct 20 the merge commit was pushed to the feature branch 46 seconds after the merge: the branch got a preview and main got no production deploy, so the live site stayed on the old build until a production deploy of main was started by hand (Vercel MCP `create_deployment`, target production, with forceNew). Main's production deploy usually starts within 5 seconds of a merge, but on Oct 21 it came 7 minutes late, so one started by hand at 3 minutes landed first (both are listed; the one Vercel builds itself has source git). After a merge, wait until main's production deploy shows up before pushing that commit anywhere else, and start it by hand only if it still hasn't come after about 10 minutes.
- An n8n run can show "success" while a step inside failed (nodes set to continue on error). Check the saved result, not the run status.
- n8n's Retry On Fail on a node set to continue on error reruns the whole node, every item again, and only when its first output item has an `error` field (n8n-core source, checked Oct 20). A failure after the first item is never retried. Apify answers an empty or private page with such an item, so the Ad Strategist's fetch has no retry.
- A manual (test) run's Execute Workflow step runs the called workflow's saved draft, not its published version (Nov 6: a Client Proposal test run got House Rules' unpublished `setup`). So a sub-workflow's draft can be tested through its callers before it is published, and a test run of a caller is not a check of the published sub-workflow.
- Supabase upsert: `Prefer: resolution=merge-duplicates`. Required columns need defaults or inserts fail silently. Use `return=representation` to see errors.
- An HTTP Request node that reads one row from PostgREST (`Accept: application/vnd.pgrst.object+json`) gets it as a text string in `data` unless its Response Format is set to JSON (Nov 6). PostgREST's `on_conflict` can't use a partial unique index (42P10): `lead_files.hs_file_id` has one, so the HubSpot sync inserts plainly and skips files it already has.
- A Code step can't open a file an earlier step downloaded: n8n keeps downloads on disk (the item's binary holds `filesystem-v2` and an id, not the bytes), and Code steps run in n8n's task runner, which offers `helpers.getBinaryDataBuffer` for the step's own input items and `helpers.httpRequest`, but not `getBinaryStream`. Read the file on the Code step's own input, or fetch it again by its link, as Lead File Text Ingest's Build Text does (Nov 6).

# 1. AI Paragon internal dashboard

## What this is
AI Paragon Consulting Group's own lead gen and marketing system. Single-file HTML app (`new-aiparagon-dashboard.html`), live on Supabase and n8n, with real Supabase Auth logins. Current goal: make it user friendly, less clutter, less text.

It's built on the demo dashboard's shell (#3, v152 design). The old v60 engine and workspace pages are ported in verbatim, CSS scoped under `.ap60`, and `apGo(view)` maps sidebar views onto v60's `state.engine/state.view` + `render()`. Don't hand-rewrite engine pages: that lost editors, run pickers, comments and the funnel package before.

## How the pieces fit
Dashboard (Vercel) → calls an n8n webhook → the n8n agent does the AI work (Claude, Tavily, SEC IAPD, Google) → writes results to Supabase → the dashboard reads Supabase and renders them. HubSpot and Slack hang off n8n. Landing pages put live from the dashboard are public: `go.html` reads a live page from Supabase and posts its sign-up form to an n8n webhook.

## Engine 1
Five agents in sequence: sector-adaptive Lead Research (RIA / other company / nonprofit), Prequalification Call Guide, Discovery Call Framework, Strategic AI Growth Plan (split into two agents to avoid timeouts). The assessment step (the anonymizer) swaps the prospect's company, email, phone and links for a placeholder firm (Delta Advisory); Discovery and the growth plan work from that, with the name and title kept. Agents use [ASSUMED:] and [FILL IN before call:] instead of pausing for missing data. A full prospect package went from about 2 hours of manual prep to about 15 minutes.
Since v136 (Erica's Nov 5 notes) the Lead pipeline is six meeting stages, each with its own prep: Prospect research (the pre-meeting prospect brief: Lead Research), Discovery consultation (the consultation guide: the interview script), Assessment (the assessment report: the anonymizer), Proposal (the proposal presentation: the growth plan, then the client proposal), Onboarding (the onboarding plan) and Client review (the client review brief), the last two by Catalyst · Meeting Prep. Moving a lead into a stage writes that stage's prep only, when the client gets there, from the documents before it and what was said in the last meeting. The discovery call framework (now the follow-up guide) is no stage's: nothing on the dashboard runs Discovery (Erica) any more, and the growth plan never needed it.
Since v137 (the second part of those notes) Catalyst starts the stages itself: a contact new in HubSpot asks to run the pre-meeting prospect brief, and a recorded call with a lead asks to file its transcript under the stage the lead is in and run the next stage with it (Today and the bell). Each stage's setup is on Templates: the meeting type, a template document, what it reads (call transcripts, the CRM record, the discovery call questions) and what it writes. Every stage run sends what its setup says it reads.
Since v138 (the gaps found in the video v7 review) a stage also reads the lead's emails logged in HubSpot, the client proposal reads the consultation guide, and the proposal, the onboarding plan and the client review draw charts (a timeline, bars) from the documents' own numbers.

# 2. Spectrum Care Advisory OS (care portal, np-demo)

## What this is
Single-file HTML portal for care agencies (`E-&-G-Home-Inc.html` in GitHub). Renamed from Meridian Care Portal at v7.5; backend names kept the np_demo prefix. Live at np.aiparagonconsulting.com. Deliveries are named np-demo-pilot-vX-Y-beta.html. Erica demos it to prospects. Pilot client is Ezra, nonprofit exec director, agency E & G Home under Alta California Regional Center. More agencies want to beta.

## How the pieces fit
The portal talks to Supabase directly for all data, logins and files, scoped per agency by RLS. Anything that leaves the portal (email, calendar, alerts, chatbot) goes portal → `np-relay` Edge Function → n8n webhook → Gmail / Google Calendar / Slack / AI model, with a no-PHI layer on outbound messages. The relay checks the signed-in user, takes the agency from the database, rate-limits each action and adds a server-side secret the n8n webhooks require.

## Compliance rules (non-negotiable)
- No PHI on external channels: extNotify sends generic text only, and everything through the relay passes extScrub (every client's UCI, name and initials, any 7-digit number, emails, phones). Ask gets labels (Client 1, Home A), never identifiers.
- Clients identified by UCI only (7 digits, 4023180). "No names" applies to clients, not staff.
- Audit entries name-scrubbed (auditScrub). Medication data removed; MAR survives as a printable blank.

check_availability, book_appointment, lookup_knowledge, escalate_to_human, end_call, read_back_number, plus reschedule_appointment and add_case_details for returning callers. read_back_number (Nov 4, defined on the assistant itself) gives back the number the caller said, from their own words on the call (the newest digits that fit what the agent heard), grouped for reading aloud; the agent reads exactly that and, once they say yes, never says the number again ("the number you gave"). Since Nov 6 it also answers when no number has been said yet: with caller ID it gives the question to ask ("Is the number you're calling from, ending in seven, seven, seven, seven, the best one to reach you?"), and without it says there is no caller ID and to ask for their number, so the prompt has no "ending in [the four caller ID digits]" template left (on calls with no caller ID the model filled it with made-up digits). reschedule_appointment on a call with no caller ID and no find_caller match says to look the caller up first, instead of "no booking on file for this number" (Nov 6). Before it, the agent read numbers back from memory, with digits added or dropped, and repeated the number in every sentence. A read-back the caller said yes to is final (Nov 6): a number passed to find_caller or book_appointment later that is a slip of those digits is taken as the confirmed number, with no second read-back, and when a read-back is needed the tool gives the exact words to say ("5 5 5... 0 1 0... 1 2 3 4. Is that right?"). Kser's Nov 6 call: find_caller got 10 of the 12 digits he had just said yes to, so the agent read them back a second time and ran two questions together ("Is that Did I get every digit?"). end_call (Nov 3) is the only way the agent hangs up (Vapi's own endCall is gone). Since Nov 4 it says nothing itself: the tool server decides from what the caller said since the agent's last question, and only then is the goodbye said. Speech-to-text stutters are folded first (Nov 4): a word said twice, a sentence said again and the start of one said again ("No. That that's it. That's it. That's it. It." was refused). The call ends only when the caller's newest words ask or add nothing: "but", "wait", "actually", "one more", "can you", a question mark, a yes, or a question or new point started at the start of a clause even when the goodbye cut it off with no question mark ("When's the inspector", "How do I pay for it", "And my neighbor", "Sorry, what was the", "I meant"; QA round 2, Nov 3), unless a goodbye of their own comes after it ("Is that it? Okay, bye." ends, "Bye. Oh wait, my gutters" doesn't). Asked to hold ("hold on", "be right back") never ends, not even on the fifth try, until they say they're back ("I'm back", "sorry about that"). Once the caller has said they're done (no, that's all, thanks, bye, or an okay), only goodbye words may follow: thanks, you too, take care, have a good one, I'll wait for his call and the like (`CLOSE_PARTS` in the tool server). Anything else after it, in the same turn or said over the goodbye ("That's all. My neighbor's roof needs a look too", "Okay, my husband says the leak is worse"), or a sentence cut off on um, and or the, means they're still talking (QA round 3, Nov 3). A hedge right after a full finish belongs to it ("That's all I think", "That's it, I guess", "I'm good I think"), but after a bare no or a full stop it starts something new ("No. I think" is still talking), and a turn of only "Now" or "Know" is speech-to-text's "No" (Nov 4). Chit-chat said before the goodbye ("No thanks. Hope the rain holds off!") gets one answer: if the agent answered it and tries again with nothing new from the caller, the call ends; words said over a goodbye never get that pass. "wait" and "hold on" count where a sentence starts, so "I'll wait for the call" is fine, and "but" and "actually" not before a finish, so "Nothing, but thank you" and "Actually, that's all" are fine. And either they said a goodbye of their own ("bye", "talk later", "have to go", "I'll call back", "I'll get back to you") or their answer to the agent's last question, a wrap-up ("anything else I can help with", "any other questions"; "anything else you'd like to add?" only once their business is done: a hand-off logged, or a booking or move made, with a number to reach them, Nov 4), is a finish (no, that's all, thanks, I don't think so, not right now, that's about it, that'll be all), counting what they said after it too ("No." then "Thank you, you too!" to the agent's "Have a great day!"). Vapi's idle prompts ("Are you still there?") are not the agent's question, and the agent's own sign-offs ("You're welcome!" then "Have a great day!") are read past to the caller's last words. Then Vapi says "Thanks for calling Pinecrest Roofing. Take care!" and hangs up after it, through its live call control (`call.monitor.controlUrl`, `{"type":"say","content":...,"endCallAfterSpoken":true}`, Nov 4); a goodbye the agent already said since the caller last spoke gets `{"type":"end-call"}` a second later instead. Otherwise it answers NOT YET with what the caller said and what to do, and the call goes on. Never stuck: after two refusals it goes through once the caller has answered again with nothing that asks or adds anything, and the fifth try always does, except on a hold (until QA round 2 the third try went through, even on "No, but would you like my house number?"). Times are Pacific, two weeks ahead, on the days and start times set on the Command Center's Settings page (`vc_settings` availability, read through `vc_tool_context`; without it, or with no days in it, Mon to Sat 8:00, 10:30, 1:00, 3:30). Nothing is offered or booked on Thanksgiving, Christmas Day or New Year's Day (fixed, not editable; a caller asking for one hears "We are closed that day for Thanksgiving"), and a day with no times says "We do not book inspections on Sundays" (Nov 2). check_availability gets the caller's words in `requested`: an open exact time is confirmed without listing others, a day and date that don't match ("Thursday the 30th" when it's a Friday) are asked about, and "Oct 20th", "Tue, Oct 20 at 10:30 AM" and "10/20 at 10:30" all read the same, as does "8 30" (speech-to-text's "eight thirty"; until Nov 3 "at 8 30" read as 8:00). Spoken dates and times read the same way (QA round 2, Nov 3): "ten thirty", "half past ten", "10 o'clock"; "8 tonight" or "8 in the evening" is 8 PM (it was confirmed as 8 AM); "the fifth of December" (it was November 5th) and "Thursday the fifth"; "tomorrow", "the day after tomorrow" (it was tomorrow), "in a week", "in two weeks"; "today", "this afternoon" and "tonight" get "Same-day times are not booked over the phone"; and Thanksgiving, Christmas and New Year's by name get the closed message; the day after, the Friday after or the Wednesday before one of them is the day meant (Nov 6: "the Friday after" Thanksgiving read as the holiday itself). A time that isn't open on a weekday with no date gets that day's closest times, never the same weekday next week. book_appointment refuses until it has a name and an address with a house number and a city (Nov 3: "Sierra Street, Tahoe City" was booked; `addressGap`), and, on a call with no caller ID and no find_caller match, a callback number of ten digits or more in `phone` (Nov 4: browser calls were booked with no number at all); escalate_to_human tells the agent to get a callback number when the call has no caller ID, no match and no full number said (`haveNumber`). It always stores the caller ID number (a different callback number goes in the note), so reschedule_appointment finds the booking on the next call. A booking made earlier on the call (its `call_id`) is the caller's (QA round 2, Nov 3): book_appointment again with a new time moves it instead of booking twice, the same time again just confirms it (it was "just taken"), and reschedule_appointment finds it on a browser call too; a different kind of visit is a booking of its own. After a high-urgency escalation the tool tells the agent that a person will call them right away, not to offer times unless the caller asks for one, and that it can't transfer the call (Nov 4; until then it said to offer the earliest leak check, and in an emergency the agent kept pushing Thursday's times). Every hand-off's answer then asks for what the coordinator needs to act fast, one question at a time and skipping what the caller already said: the property address (house number, street and city), the last name when only a first was given, and where the damage is and since when (`NEED_DETAILS`, Nov 6; Kser's urgent call never got his address). If lookup_knowledge says a topic belongs to a person, the agent says what it's told and escalates. If it says to ask questions first, the agent asks only the ones it still needs, one at a time. Two-word first names (Nov 2): a name that is the start of the other (Mary Ann and Mary Ann Smith) fits, and asks for the last name when the caller gave less than the file has; a shorter name on file never stands in for a fuller one on the same number. Jr., Sr., II and III are kept apart from the name (QA round 2, Nov 3): one side without one still fits ("Robert Lee" and "Robert Lee Jr."; the agent used to ask for a last name it had just been given), two different ones never do (a father and son on one phone). `vc_name_fits` in Supabase follows the same rules. It answers MATCH (the file, without address, email or number), CHECK (one thing to ask) or NO MATCH / NO FILE (a new caller; it never says whose the number is), at most three tries a call. # 5. Website builder demo (Puck)

## What this is
A self-serve website builder demo for the website creation offer (Erica's guide "Building Cinematic Websites with Claude", Oct 14). A dashboard of pages, a New page dialog (Cinematic, Business, Blank or Describe it), a visual editor built on Puck (open source, MIT) where a page is made of sections, and the published page. Users click to type on the page, drag sections in, change settings in a side panel, preview phone, tablet and desktop, ask the AI to write the page or change it, and set the page's SEO, its own domain, a chatbot and custom code (tracking tags and their own code). Signed in with an AI Paragon account, pages are the team's: saved in their own Supabase project as you edit, the same on any computer, and Publish puts a page on the web at sites.aiparagonconsulting.com/<page> and at its own domain, drawn on the server, with its chatbot answering visitors (see Hosting). Signed out, pages are kept in the browser (localStorage `apSiteBuilder.v1`) as before, with the two sample pages. Clients have no accounts yet.

## How it's built
- Source in `builder-src/` (React 19, `@puckeditor/core` 0.23, esbuild). From `builder-src/`: `npm install`, then `npm run build` writes `site-builder.html`, one file with the script and styles inlined and the bundled packages' licenses at the end. Never edit `site-builder.html` by hand: change the source, rebuild, commit both. `.vercelignore` keeps `builder-src/` off the live site; its node_modules stay out of git.
- `src/blocks.jsx`: the sections (Menu bar, Hero, Scroll story, Feature cards, Steps, Text and visual, FAQ, Call to action, Footer, Heading, Text, Button, Spacer), their fields and how they render. One config renders both the editor canvas and the published page. `src/blocks.css` styles built pages (scoped under `.sb-site`). `src/templates.js`: the starting points. `src/store.js`: pages (a draft and a live copy each; status Draft, Live or Unpublished changes), each either the team's (`where: 'team'`) or this browser's (`'local'`; see Hosting). `src/router.js`: addresses. `src/main.jsx`: dashboard, editor, preview. `src/app.css`: the builder's own look (AI Paragon tokens, as in go.html).
- Motion: Hero backgrounds are particles that follow the cursor, aurora, a moving grid, a video or an image. The Scroll story is a full-screen scene that sticks while its chapters scroll over it, driven by `--p` (scroll progress 0 to 1): Deep space, Neon city, Warp tunnel, or the user's video scrubbed by the scroll. Scenes are drawn in CSS, no media files. Entrance animations only run on the published page, never in the editor; prefers-reduced-motion holds everything still with every word visible.
- Puck's built-in Publish control is a span a keyboard cannot reach, so the header has our own Publish button (`HeaderActions`). The canvas does not wait for web fonts (`iframe.waitForStyles` false).
- The AI (v2): `src/ai.js` is its side of the Site Builder · AI workflow. `catalog()` writes the blocks, fields and options from the Puck config, so a new block or option reaches the AI with no change in n8n (a new block needs a line in `ABOUT`, a field that only counts with a choice one in `WHEN`); `pageForAi` is the page as the AI reads it (settings without the address, then each section's id, type and fields); `askAi` sends both with the request and the sign-in token and waits up to 150 seconds. Claude answers with the page's sections in order, each `{keep: id}`, `{edit: id, props}` (only the fields that change; a list replaces the whole list) or `{add: type, props}`; a section left out is removed. `applyAnswer` checks it before anything touches the page: known blocks, fields and options only, text tidied and capped, rich text cut down to p, strong, em, a, ul, ol and li, a web address, email or phone number only when it is in the request or already on the page (else #), pictures and videos only from an https address given (else the built-in look), new ids for added sections, and sections added while the AI worked kept at the end.
- `src/auth.js`: the AI's sign-in, with the team's accounts on the shared Supabase project (the dashboard's). The builder keeps its own session under `apSiteBuilder.auth` and renews it one tab at a time (`navigator.locks`). A dashboard sign-in in the same browser (`ap.session.v1`) is used while it has more than a minute left, read only: the builder never renews it, since two apps renewing one session race for the same renewal key.
- `src/AiPanel.jsx`: the AI tab (a Puck plugin, after Blocks and Outline) and `useAiSession`, which holds the request, the answer, Undo and a description waiting from Describe it in the editor view (see Gotchas). The header's Ask AI button opens the tab and puts the cursor in it. An answer goes in through Puck's setData with history on, so Puck's undo takes it back too; Undo this change shows only while the page is as the AI left it. `src/context.js` holds `EditorCtx`. Tests reach the checks through `window.__SB_TEST__`, filled only when a test sets it to true before load.
- Page settings (v3): the editor's left rail has SEO, Domain, Chatbot and Code tabs after AI (`src/SettingsPanels.jsx`), and the header's Settings button opens SEO (the rail items are divs a keyboard cannot reach; each tab has buttons for the others). SEO, the chatbot and custom code are page settings with no field in Puck's page panel (root props `seoTitle`, `socialImage`, `noindex`, `chatbot`, `tracking`, `code`), changed with `replaceRoot` like Puck's own fields, so they autosave, go live with Publish and undo. The domain and the chatbot's contacts are kept on the page record (`page.domain`, `page.leads`, store.js): not content, so they neither wait for Publish nor mark the page changed.
- `src/seo.js`: what search engines read (`seoOf`: the title in Google falls back to the page name, only https pictures), the checks (title 30 to 60 characters, description 70 to 155, one Hero headline, pictures described, no [bracket] placeholders left, no buttons or links to #, a picture for link previews) and `applyMeta`, which writes the title, description, robots, Open Graph, X card and canonical tags while the published view is open and puts the builder's own back after (a draft preview is always noindex, with no canonical).
- `src/domain.js`: what counts as a domain (`normalizeDomain`), the records it will need (`recordsFor`: two A records for a bare domain, a CNAME for www and other subdomains; a bare domain gets www too and the other way round) and the live check (`checkDns`: DNS over HTTPS at dns.google, then cloudflare-dns.com, for the domain and its www or bare pair).
- `src/chat.js` and `src/ChatWidget.jsx`: the chatbot. Its settings (`botOf`: name, first message, what it should know, rules, tone, up to three suggested questions (else the first three from the page's FAQ), the contact details to ask for (name and email, plus phone, or none), a booking or contact link and its button text, the chat button's text and corner), the page as it reads it (`pageTextFor`: each section's words under its name, no links, ids or picture addresses, 12,000 characters at most), and its two ways to answer: `askBot` (`src/chat-team.js`: the builder's Try it and previews; sends the token, the settings, the draft's words and the last 12 turns, waits up to 45 seconds) and `visitorChat` (`src/chat-visitor.js`: a live page; sends only the page id and the turns, or a contact). The window takes its `ask` from its caller. An answer's action brings the contact form (`contact`, unless contact details are off) or the booking button (`link`, only with a link set). The page root renders it (`ChatMount`) on the draft preview and the live page, never on the editor canvas; `PageCtx` (context.js) tells it the page, its words and where contacts go. The Chatbot tab shows the same window inline to try it.
- `src/code.js`: custom code (v3.1), like Webflow's. Tracking IDs for Google Analytics 4, Google Tag Manager, Meta Pixel, LinkedIn Insight Tag and HubSpot (`trackerError` says why an ID is not one), each service's own tag with the ID filled in (`pageCode`: Tag Manager first in the head and right after the body opens, then the others; the team's head code after the tags, its body code before them), and `checkCode`, which reads pasted code with DOMParser (nothing runs, nothing loads): the services it recognises, the sites it loads from, what it holds, and what to fix (body tags or loose text in the head, text outside any tag, an unclosed script or style tag, http links, a service both in its box and in the code). None of it ever runs in the builder; the live page's server puts it in place (see Gotchas).
- Links typed into the editor go through `safeHref` (a javascript: link becomes #).

## Gotchas
- Puck builds its sidebar twice as the editor opens: a plugin's panel mounts, unmounts and mounts again. Anything that has to live on goes in the editor view (`useAiSession`), not in the panel; before that, a Describe it description went to the AI twice and the first request was cut off.
- Puck's rail items (Blocks, Outline, AI) are divs and its Publish control a span, none reachable by keyboard; the header has real buttons for Ask AI and Publish.
- Puck's Delete and Backspace hotkeys remove the selected section unless the key comes from an input, a textarea or editable text, so the AI box is safe (tested).
- The workflow answers in one call, no polling: a whole page took about 15 seconds on Oct 28. The builder waits up to 150 seconds, and a 524 or 504 from a proxy in between reads as "took too long".
- Puck keeps every plugin panel mounted and shows one, so ids must differ across tabs (the Chatbot tab's sign-in uses `chat-` ids, the AI tab's `ai-`) and work meant for the tab on screen checks `ui.plugin.current` (the Domain tab reads DNS only while it shows).
- Puck makes edits within 300 ms one undo step (its history is debounced), so a burst of typing undoes together.
- A grid inside a side panel needs `grid-template-columns: minmax(0, 1fr)`, or a wide child (the chat window) widens the panel past Puck's sidebar. The chat window scrolls its own log (`scrollTop`): scrollIntoView also scrolled Puck's sidebar sideways.
- Custom code never runs on aiparagon.vercel.app, not in the editor or the builder's previews: they share the address with the dashboard (its sign-in is kept in the browser there) and the other apps, so a pasted script could read the team's sign-ins. In the builder it is only ever read (`checkCode` uses DOMParser, whose documents run nothing and load nothing) and shown as text; never put it in the builder's page (no dangerouslySetInnerHTML, no appended script). It runs only on live pages, which the aiparagon-sites server puts it into, on their own addresses.
- Live pages share sites.aiparagonconsulting.com, a subdomain of the company's domain, so a page's code there could set cookies for every *.aiparagonconsulting.com address (n8n, the care portal). Fine while only the team publishes; before clients can publish code of their own, move the shared link to a domain of its own (like Webflow's webflow.io).
- The builder opens the team's pages as it loads, which renews a team sign-in that is about to run out (the AI suite's refused renewal now happens there).
- `.ap-top` has a blur (backdrop-filter), which holds any fixed element inside it to the header: dialogs render on `document.body` (`createPortal` in `Modal`), or Sign in and Sign out would open a dialog squeezed into the header.
- Puck's own server renderer (`@puckeditor/core/rsc`) pulls in its rich text editor (Tiptap, ProseMirror, about 330 KB); the sections have no rich text fields, slots or drop zones, so live pages draw with `src/site/render.jsx`. A new section using those needs it there too.
- n8n's Code node has no `URL()`, so the Visitor Chat reads the Origin host with a pattern.
- The visitor chat's Origin check names the shared link and `aiparagon-sites(-…)?.vercel.app`: a Vercel project with another name would need the pattern changed in its Decide step.
- The build refuses `<!--` in the inline script (it can break the page's script tag), so the services' tags in code.js leave out their comment lines.
- The DNS values in domain.js come from Vercel's domain config for this team (Nov 2): A 216.198.79.1 and 64.29.17.1 (76.76.21.21 still accepted) and the general CNAME cname.vercel-dns.com. A hosting project's own CNAME is only known once that project exists.
